# SIMS Mobile API — v1

JSON API used by the SIMS mobile app (React Native / Expo). It runs inside the
same Laravel app and database as the website.

- **Who can use it:** every **active** account with a SIMS role: Student (1), Internship
  Coordinator (2), Supervisor (3), Administrator (4). Accounts with no role are refused.
  What each role may do is the same as on the website; every endpoint enforces it.
- **Status:** Module 1 (auth foundation). New endpoints are added per module; existing
  fields are never renamed or removed within `v1` — only new fields/endpoints are added.

## Basics

| | |
|---|---|
| Base URL | `https://<your-domain>/api/v1` (local: `http://127.0.0.1:8000/api/v1`) |
| Request body | JSON (`Content-Type: application/json`). File uploads (later modules) use `multipart/form-data`. |
| Response body | Always JSON (`Content-Type: application/json`), except `204 No Content`. The API never returns HTML or redirects. |
| Recommended headers | `Accept: application/json` on every request |
| Auth | `Authorization: Bearer <token>` on every endpoint except `POST /login` |
| Dates/times | App timezone is `Asia/Manila` (fields added in later modules will state their format) |

### Tokens

- A token is returned by `POST /login`. It looks like `12|Xb4Q...` (an id, a `|`, then 40 random characters). Treat it as opaque; store it in `expo-secure-store`.
- Tokens **do not expire by time**. They stop working when:
  - the app calls `POST /logout` (revokes only that device's token), or
  - an admin or coordinator deactivates the account or changes its role on the website — all of that user's tokens are deleted at that moment, so the next request gets `401`, or
  - the account is otherwise found inactive, or without a role, when a request arrives — that request gets `403` with a `code` (see below) and the token is deleted on the server.
- One token per device login; logging in on a second device does not sign out the first.

## Error format

Every error is JSON with at least a `message`:

```json
{ "message": "Human readable text." }
```

| Status | When | Body |
|---|---|---|
| `401` | Missing, invalid, or revoked token | `{"message": "Unauthenticated."}` |
| `403` | Not allowed. From the auth layer it carries a `code` (below); from a role check on a specific endpoint it is just `{message}` | `{"message": "...", "code": "..."}` or `{"message": "..."}` |
| `404` | Unknown URL or a record that doesn't exist / isn't yours to see | `{"message": "Not found."}` |
| `405` | Wrong HTTP method for the URL | `{"message": "Method not allowed."}` |
| `422` | Validation failed | `{"message": "...", "errors": {"field": ["msg", ...]}}` |
| `429` | Rate limited. `Retry-After` header = seconds to wait | `{"message": "Too Many Attempts."}` |
| `500` | Server error | `{"message": "Server Error"}` |

Any request field (query or body, at any nesting depth) that isn't valid UTF-8 text is rejected
on every endpoint with `422` before anything else runs: `errors[field] = ["The <field> field must be valid UTF-8 text."]`
(nested fields use dot keys like `meta.a`; a malformed field *name* is reported under `input`).

`422` `errors` keys are the request field names. `message` is the first error (plus "(and N more errors)" when there are several) — show `errors[field][0]` next to each field.

### 403 `code` values

| `code` | `message` | App should |
|---|---|---|
| `role_not_allowed` | `This account does not have access to the mobile app.` | Clear the stored token, show the message on the login screen. Only sent for an account with no role (rare data problem); all four SIMS roles are allowed. |
| `account_inactive` | `This account has been deactivated. Please contact an administrator.` | Clear the stored token, show the message on the login screen |

When either comes back from an **authenticated** endpoint the server has already deleted the token, so the app must treat it like a logout. Treat any `401` the same way.

### Rate limits

| Endpoint(s) | Limit | Key |
|---|---|---|
| `POST /login` | 5 requests / minute (all attempts, successful or not) | account + client IP (see below) |
| All authenticated endpoints | 120 requests / minute | user |
| All authenticated endpoints, requests that end in `401` (missing/invalid/revoked token) | 60 / minute; past that, **every** request from that IP gets `429` until the minute is up | client IP |

Responses under a limit include `X-RateLimit-Limit` and `X-RateLimit-Remaining`; a `429` adds `Retry-After`.

The login key can't be dodged by re-spelling the email: if the address matches an account (the
database ignores case, accents, full-width letters, zero-width characters and trailing spaces)
the key is that account; otherwise it is the email with whitespace/invisible characters removed,
normalised and lower-cased. A non-string `email` is a normal `422`.

The website login shares **the same counter**: 5 attempts per minute per account + IP in total
across the app and the website (every app attempt counts; the website counts its failed attempts
and resets the counter when someone logs in there successfully). After 5 wrong passwords on the
website, the app gets `429` too, and the other way round.

**Client IP behind a proxy (deployment):** `X-Forwarded-*` headers are only trusted from the
addresses in the `TRUSTED_PROXIES` env variable (see `config/trustedproxy.php`). The default is
loopback (`127.0.0.1,::1`), which covers ngrok and an nginx/Apache reverse proxy on the same
server; set a comma-separated list of IPs/CIDRs for a remote load balancer, or `none`. Never use
`*` on a server that is reachable directly, because a client could then fake its IP to reset its login limit.

## Shared objects

### User

```json
{
  "id": 42,
  "name": "Juan Dela Cruz",
  "email": "juan@example.com",
  "role_id": 1,
  "role": "Student"
}
```

| Field | Type | Notes |
|---|---|---|
| `id` | int | |
| `name` | string | |
| `email` | string | |
| `role_id` | int | `1` Student, `2` Internship Coordinator, `3` Supervisor, `4` Administrator |
| `role` | string | `"Student"`, `"Internship Coordinator"`, `"Supervisor"` or `"Administrator"` (display name; branch on `role_id`) |

### StudentProfile

```json
{
  "id": 7,
  "student_number": "2026-00001",
  "course": "BSIT",
  "section": "A",
  "internship_status": "ongoing",
  "required_hours": 486,
  "company": { "id": 3, "name": "Acme Corp" },
  "supervisor": { "id": 15, "name": "Maria Santos" }
}
```

| Field | Type | Notes |
|---|---|---|
| `id` | int | Student record id (not the user id) |
| `student_number` | string | |
| `course` | string | |
| `section` | string | |
| `internship_status` | string | `not_started` \| `ongoing` \| `completed` |
| `required_hours` | int \| null | `null` = not set yet |
| `company` | `{id: int, name: string}` \| null | `null` = not assigned to a company yet |
| `supervisor` | `{id: int, name: string}` \| null | `null` = no supervisor assigned yet |

### StaffPermissions

Returned as `staff` by `GET /me` for Coordinators (2) and Administrators (4) so the app can
build their navigation. They mirror the website's access rules and are **UI hints only**:
every endpoint still checks the role itself and answers `403` if not allowed. New flags may be
added within `v1`; existing ones are never renamed or removed.

| Flag | Coordinator | Admin | Meaning |
|---|---|---|---|
| `can_manage_users` | `true` | `true` | User Management (Students self-register and can't be created here; Coordinators can't create or promote Administrators — enforced by the server) |
| `can_manage_companies` | `true` | `true` | Company Management + Supervisor Roster |
| `can_assign_internships` | `true` | `true` | Internship Assignment |
| `can_approve_attendance` | `false` | `true` | Pending Approvals (approve / reject time-in and time-out) |
| `can_edit_attendance` | `false` | `true` | Attendance Monitoring writes (manual entries, required hours); without it monitoring is view-only |
| `can_review_reports` | `true` | `true` | Report Reviews: review / comment |
| `can_write_evaluations` | `false` | `true` | Supervisor Evaluations: create / edit draft / submit; without it evaluations are view-only |
| `can_lock_evaluations` | `false` | `true` | Supervisor Evaluations: lock / reopen |
| `can_manage_criteria` | `false` | `true` | Evaluation Criteria management |

Both staff roles can always view Dashboard/Analytics, Attendance and Progress Monitoring,
Report Reviews, Supervisor Evaluations and Notifications, so those have no flag.

## Endpoints

### `POST /login`

No auth. Exchanges credentials for a token.

Request:

```json
{
  "email": "juan@example.com",
  "password": "secret",
  "device_name": "Juan's Galaxy A54"
}
```

| Field | Rules |
|---|---|
| `email` | required, valid email, max 255 |
| `password` | required, string |
| `device_name` | required, string, max 255 — shown to the user later as the device list; use e.g. `Device.modelName` |

**200 OK**

```json
{
  "token": "12|Xb4QkPz8mN2...",
  "user": {
    "id": 42,
    "name": "Juan Dela Cruz",
    "email": "juan@example.com",
    "role_id": 1,
    "role": "Student"
  }
}
```

**422** wrong email *or* wrong password (identical response either way — it never reveals whether the email exists):

```json
{
  "message": "These credentials do not match our records.",
  "errors": { "email": ["These credentials do not match our records."] }
}
```

**422** missing/invalid fields:

```json
{
  "message": "The email field is required. (and 2 more errors)",
  "errors": {
    "email": ["The email field is required."],
    "password": ["The password field is required."],
    "device_name": ["The device name field is required."]
  }
}
```

**200** is returned for an active account of any of the four roles (`user.role_id` 1–4).

**403** correct password but the account has no role (data problem — contact an administrator):

```json
{
  "message": "This account does not have access to the mobile app.",
  "code": "role_not_allowed"
}
```

**403** correct password but deactivated account:

```json
{
  "message": "This account has been deactivated. Please contact an administrator.",
  "code": "account_inactive"
}
```

**429** more than 5 attempts in a minute for this email from this IP:

```json
{ "message": "Too Many Attempts." }
```

### `POST /logout`

Auth required. Revokes **only the token used for this request**; other devices stay signed in.

**204 No Content** (empty body).

**401** if the token is already invalid — the app should still clear its stored token.

### `GET /me`

Auth required. The signed-in user plus a role-specific summary. The response always has the
four keys `user`, `student`, `supervisor`, `staff`; the one matching the role is filled and the
other two are always `null`:

| `user.role_id` | `student` | `supervisor` | `staff` |
|---|---|---|---|
| 1 Student | StudentProfile \| null | `null` | `null` |
| 2 Internship Coordinator | `null` | `null` | StaffPermissions |
| 3 Supervisor | `null` | `{students_count}` | `null` |
| 4 Administrator | `null` | `null` | StaffPermissions |

**200 OK — Student**

```json
{
  "user": {
    "id": 42,
    "name": "Juan Dela Cruz",
    "email": "juan@example.com",
    "role_id": 1,
    "role": "Student"
  },
  "student": {
    "id": 7,
    "student_number": "2026-00001",
    "course": "BSIT",
    "section": "A",
    "internship_status": "ongoing",
    "required_hours": 486,
    "company": { "id": 3, "name": "Acme Corp" },
    "supervisor": { "id": 15, "name": "Maria Santos" }
  },
  "supervisor": null,
  "staff": null
}
```

A Student account may (rarely) have no student profile yet; then `"student": null`. The app should show a "profile not set up — contact your coordinator" state instead of crashing.

**200 OK — Supervisor**

```json
{
  "user": {
    "id": 15,
    "name": "Maria Santos",
    "email": "maria@example.com",
    "role_id": 3,
    "role": "Supervisor"
  },
  "student": null,
  "supervisor": { "students_count": 12 },
  "staff": null
}
```

`students_count` = students whose assigned supervisor is this user.

**200 OK — Internship Coordinator**

```json
{
  "user": {
    "id": 3,
    "name": "Ana Reyes",
    "email": "ana@example.com",
    "role_id": 2,
    "role": "Internship Coordinator"
  },
  "student": null,
  "supervisor": null,
  "staff": {
    "can_manage_users": true,
    "can_manage_companies": true,
    "can_assign_internships": true,
    "can_approve_attendance": false,
    "can_edit_attendance": false,
    "can_review_reports": true,
    "can_write_evaluations": false,
    "can_lock_evaluations": false,
    "can_manage_criteria": false
  }
}
```

**200 OK — Administrator**: same shape with `role_id: 4`, `role: "Administrator"` and every
`staff` flag `true` (see [StaffPermissions](#staffpermissions)).

**401** / **403** (`code`) as described above.

## curl quick start

```bash
# Log in
curl -s -X POST http://127.0.0.1:8000/api/v1/login \
  -H "Accept: application/json" -H "Content-Type: application/json" \
  -d '{"email":"juan@example.com","password":"secret","device_name":"curl"}'

# Use the token
curl -s http://127.0.0.1:8000/api/v1/me \
  -H "Accept: application/json" -H "Authorization: Bearer 12|Xb4QkPz8mN2..."

# Log out
curl -s -X POST http://127.0.0.1:8000/api/v1/logout \
  -H "Accept: application/json" -H "Authorization: Bearer 12|Xb4QkPz8mN2..."
```

## Changelog

- **Module 1** — `POST /login`, `POST /logout`, `GET /me`; error format; rate limits.
- **Module 1 revision (2026-10-02)** — the API is open to all four roles. Coordinators and
  Administrators can log in (previously `403 role_not_allowed`); `role_not_allowed` now only
  covers accounts with no role and has a new message. `GET /me` gained the `staff` key
  (StaffPermissions for roles 2/4, `null` otherwise).
