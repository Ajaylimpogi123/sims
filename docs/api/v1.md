# SIMS Mobile API — v1

JSON API used by the SIMS mobile app (React Native / Expo). It runs inside the
same Laravel app and database as the website.

- **Who can use it:** every **active** account with a SIMS role: Student (1), Internship
  Coordinator (2), Supervisor (3), Administrator (4). Accounts with no role are refused.
  What each role may do is the same as on the website; every endpoint enforces it.
- **Status:** Module 1 (auth foundation), Module 4 (notifications), Module 5 (dashboards & analytics), Module 6 (student attendance), Module 7 (student reports), Module 8 (student feedback), Module 9 (pending approvals). New endpoints are added per module; existing
  fields are never renamed or removed within `v1` — only new fields/endpoints are added.

## Basics

| | |
|---|---|
| Base URL | `https://<your-domain>/api/v1` (local: `http://127.0.0.1:8000/api/v1`) |
| Request body | JSON (`Content-Type: application/json`). File uploads (attendance photos, report attachments) use `multipart/form-data`. |
| Response body | Always JSON (`Content-Type: application/json`), except `204 No Content`. The API never returns HTML or redirects. |
| Recommended headers | `Accept: application/json` on every request |
| Auth | `Authorization: Bearer <token>` on every endpoint except `POST /login` |
| Dates/times | App timezone is `Asia/Manila`; date-times are ISO 8601 with offset, e.g. `2026-10-02T14:03:00+08:00` |

### Tokens

- A token is returned by `POST /login`. It looks like `12|Xb4Q...` (an id, a `|`, then 40 random characters). Treat it as opaque; store it in `expo-secure-store`.
- Tokens **do not expire by time**. They stop working when:
  - the app calls `POST /logout` (revokes only that device's token), or
  - an admin or coordinator deactivates the account or changes its role on the website — all of that user's tokens are deleted at that moment, so the next request gets `401`, or
  - the account is otherwise found inactive, or without a role, when a request arrives — that request gets `403` with a `code` (see below) and the token is deleted on the server.
- One token per device login; logging in on a second device does not sign out the first.

## Error format

Every error is JSON with at least a `message`:

```json
{ "message": "Human readable text." }
```

| Status | When | Body |
|---|---|---|
| `401` | Missing, invalid, or revoked token | `{"message": "Unauthenticated."}` |
| `403` | Not allowed. From the auth layer it carries a `code` (below); from a role check on a specific endpoint it is just `{message}` | `{"message": "...", "code": "..."}` or `{"message": "..."}` |
| `404` | Unknown URL or a record that doesn't exist / isn't yours to see | `{"message": "Not found."}` |
| `405` | Wrong HTTP method for the URL | `{"message": "Method not allowed."}` |
| `422` | Validation failed | `{"message": "...", "errors": {"field": ["msg", ...]}}` |
| `429` | Rate limited. `Retry-After` header = seconds to wait | `{"message": "Too Many Attempts."}` |
| `500` | Server error | `{"message": "Server Error"}` |

Any request field (query or body, at any nesting depth) that isn't valid UTF-8 text is rejected
on every endpoint with `422` before anything else runs: `errors[field] = ["The <field> field must be valid UTF-8 text."]`
(nested fields use dot keys like `meta.a`; a malformed field *name* is reported under `input`).

`422` `errors` keys are the request field names. `message` is the first error (plus "(and N more errors)" when there are several) — show `errors[field][0]` next to each field.

### 403 `code` values

| `code` | `message` | App should |
|---|---|---|
| `role_not_allowed` | `This account does not have access to the mobile app.` | Clear the stored token, show the message on the login screen. Only sent for an account with no role (rare data problem); all four SIMS roles are allowed. |
| `account_inactive` | `This account has been deactivated. Please contact an administrator.` | Clear the stored token, show the message on the login screen |

When either comes back from an **authenticated** endpoint the server has already deleted the token, so the app must treat it like a logout. Treat any `401` the same way.

### Rate limits

| Endpoint(s) | Limit | Key |
|---|---|---|
| `POST /login` | 5 requests / minute (all attempts, successful or not) | account + client IP (see below) |
| All authenticated endpoints | 120 requests / minute | user |
| All authenticated endpoints, requests whose token can't be real (missing, malformed, unknown or revoked id, wrong secret) | 60 / minute; past that, such requests from that IP get `429` instead of `401` until the minute is up | client IP |

A real, valid token (sent in full, `<id>|<secret>` exactly as returned by `POST /login`; the
secret alone is treated as malformed by this limit) is never throttled by that last limit, even when others on the same IP
(campus Wi-Fi, mobile-carrier NAT) send junk. Over the limit, malformed tokens are refused
before any database lookup; well-formed ones are still checked, and only fakes get `429`.
Treat a `429` as "wait `Retry-After` seconds", not as a logout.

Responses under a limit include `X-RateLimit-Limit` and `X-RateLimit-Remaining`; a `429` adds `Retry-After`.

The login key can't be dodged by re-spelling the email: if the address matches an account (the
database ignores case, accents, full-width letters, zero-width characters and trailing spaces)
the key is that account; otherwise it is the email with whitespace/invisible characters removed,
normalised and lower-cased. A non-string `email` is a normal `422`.

The website login shares **the same counter**: 5 attempts per minute per account + IP in total
across the app and the website (every app attempt counts; the website counts its failed attempts
and resets the counter when someone logs in there successfully). After 5 wrong passwords on the
website, the app gets `429` too, and the other way round.

**Client IP behind a proxy (deployment):** `X-Forwarded-*` headers are only trusted from the
addresses in the `TRUSTED_PROXIES` env variable (see `config/trustedproxy.php`). The default is
loopback (`127.0.0.1,::1`), which covers ngrok and an nginx/Apache reverse proxy on the same
server; set a comma-separated list of IPs/CIDRs for a remote load balancer, or `none`. Never use
`*` on a server that is reachable directly, because a client could then fake its IP to reset its login limit.

### StaffPermissions

Returned as `staff` by `GET /me` for Coordinators (2) and Administrators (4) so the app can
build their navigation. They mirror the website's access rules and are **UI hints only**:
every endpoint still checks the role itself and answers `403` if not allowed. New flags may be
added within `v1`; existing ones are never renamed or removed.

| Flag | Coordinator | Admin | Meaning |
|---|---|---|---|
| `can_manage_users` | `true` | `true` | User Management (Students self-register and can't be created here; Coordinators can't create or promote Administrators — enforced by the server) |
| `can_manage_companies` | `true` | `true` | Company Management + Supervisor Roster |
| `can_assign_internships` | `true` | `true` | Internship Assignment |
| `can_approve_attendance` | `false` | `true` | Pending Approvals (approve / reject time-in and time-out) |
| `can_edit_attendance` | `false` | `true` | Attendance Monitoring writes (manual entries, required hours); without it monitoring is view-only |
| `can_review_reports` | `true` | `true` | Report Reviews: review / comment |
| `can_write_evaluations` | `false` | `true` | Supervisor Evaluations: create / edit draft / submit; without it evaluations are view-only |
| `can_lock_evaluations` | `false` | `true` | Supervisor Evaluations: lock / reopen |
| `can_manage_criteria` | `false` | `true` | Evaluation Criteria management |

Both staff roles can always view Dashboard/Analytics, Attendance and Progress Monitoring,
Report Reviews, Supervisor Evaluations and Notifications, so those have no flag.

## Endpoints

### `POST /login`

No auth. Exchanges credentials for a token.

Request:

```json
{
  "email": "juan@example.com",
  "password": "secret",
  "device_name": "Juan's Galaxy A54"
}
```

| Field | Rules |
|---|---|
| `email` | required, valid email, max 255 |
| `password` | required, string |
| `device_name` | required, string, max 255 — shown to the user later as the device list; use e.g. `Device.modelName` |

**200 OK**

```json
{
  "token": "12|Xb4QkPz8mN2...",
  "user": {
    "id": 42,
    "name": "Juan Dela Cruz",
    "email": "juan@example.com",
    "role_id": 1,
    "role": "Student"
  }
}
```

**422** wrong email *or* wrong password (identical response either way — it never reveals whether the email exists):

```json
{
  "message": "These credentials do not match our records.",
  "errors": { "email": ["These credentials do not match our records."] }
}
```

**422** missing/invalid fields:

```json
{
  "message": "The email field is required. (and 2 more errors)",
  "errors": {
    "email": ["The email field is required."],
    "password": ["The password field is required."],
    "device_name": ["The device name field is required."]
  }
}
```

**200** is returned for an active account of any of the four roles (`user.role_id` 1–4).

**403** correct password but the account has no role (data problem — contact an administrator):

```json
{
  "message": "This account does not have access to the mobile app.",
  "code": "role_not_allowed"
}
```

**403** correct password but deactivated account:

```json
{
  "message": "This account has been deactivated. Please contact an administrator.",
  "code": "account_inactive"
}
```

**429** more than 5 attempts in a minute for this email from this IP:

```json
{ "message": "Too Many Attempts." }
```

### `POST /logout`

Auth required. Revokes **only the token used for this request**; other devices stay signed in.

**204 No Content** (empty body).

**401** if the token is already invalid — the app should still clear its stored token.

### Notifications

Every role (1–4). Each user only ever sees and changes **their own** notifications; nothing
here accepts a user id. These endpoints share the normal 120 requests / minute per-user limit,
so polling `GET /notifications/unread-count` about once a minute while the app is in the
foreground is fine.

#### Notification object

```json
{
  "id": 123,
  "type": "attendance_pending",
  "title": "New attendance approval request",
  "message": "Juan Dela Cruz submitted a time-in for October 2, 2026 awaiting your approval.",
  "read_at": null,
  "created_at": "2026-10-02T14:03:00+08:00",
  "target": { "screen": "approvals", "params": { "attendance_id": 55 } }
}
```

| Field | Type | Notes |
|---|---|---|
| `id` | int | |
| `type` | string | `attendance_pending`, `attendance_reviewed`, `report_submitted`, `report_reviewed`, `assignment_updated`, `student_registered`. More may be added within `v1`, so show unknown types normally |
| `title` | string | Same text as the website |
| `message` | string \| null | The body text the website shows under the title |
| `read_at` | string \| null | ISO 8601 with offset (`+08:00`); `null` = unread |
| `created_at` | string | ISO 8601 with offset (`+08:00`) |
| `target` | `{screen, params}` \| null | Which app screen a tap should open, resolved for **the signed-in user's current role** (see below). `null` = no specific screen, so just mark it read (the website opens the inbox in that case) |

#### `target` screens

`screen` values are the app's feature keys. They are stable: never renamed within `v1`, though
new ones may be added. The app should treat a screen it doesn't know like `null`. `params` is
always an object (`{}` when empty) whose values are ints. They are **highlight hints only**: the
record may have been deleted since, so the screen must open normally if it can't find the record.
Params are present exactly where the website highlights a row (`?highlight=`).

| `type` | Student (1) | Coordinator (2) | Supervisor (3) | Administrator (4) |
|---|---|---|---|---|
| `attendance_pending` | `null` | `attendance-monitoring` `{}` ¹ | `approvals` `{attendance_id}` | `approvals` `{attendance_id}` |
| `attendance_reviewed` | `attendance` `{attendance_id}` | `attendance-monitoring` `{}` | `attendance-monitoring` `{}` | `attendance-monitoring` `{}` |
| `report_submitted` | `null` | `report-reviews` `{report_id}` | `report-reviews` `{report_id}` | `report-reviews` `{report_id}` |
| `report_reviewed` | `my-reports` `{report_id}` | `report-reviews` `{report_id}` | `report-reviews` `{report_id}` | `report-reviews` `{report_id}` |
| `assignment_updated` | `home` `{}` | `students` `{}` | `progress` `{}` | `students` `{}` |
| `student_registered` | `null` | `students` `{}` | `null` | `students` `{}` |
| any other type, or the notification lacks its record id | `null` | `null` | `null` | `null` |

¹ Older rows from before approvals moved to Supervisor/Administrator; Coordinators view attendance read-only.

| `screen` | Website page | Roles it is ever sent to |
|---|---|---|
| `approvals` | Pending Approvals | Supervisor, Administrator |
| `attendance-monitoring` | Attendance Monitoring | Coordinator, Supervisor, Administrator |
| `attendance` | My Attendance | Student |
| `report-reviews` | Report Reviews | Coordinator, Supervisor, Administrator |
| `my-reports` | My Reports | Student |
| `home` | Dashboard | Student |
| `progress` | Progress Monitoring | Supervisor |
| `students` | Internship Assignment | Coordinator, Administrator |
| `evaluations` | Supervisor Evaluations | Coordinator, Supervisor, Administrator (dashboard action items only, see below) |

The server never targets a screen the viewer's role can't open. The same table drives the website's
notification links (`NotificationService::urlFor()` / `targetFor()`), so the app and the website
always open the equivalent page. Dashboard [action items](#action-items) use the same screen keys
(`App\Support\AppScreen`).

#### `GET /notifications`

Newest first (`created_at`, then `id`, descending). **Cursor pagination:** items that arrive while
the user scrolls never shift a page, so nothing is shown twice. Pull-to-refresh = request again
without `cursor`.

| Query | Rules |
|---|---|
| `unread` | optional; `1`/`true` = unread only, `0`/`false` (or omitted) = all |
| `per_page` | optional int, 1–50, default 20 |
| `cursor` | optional; pass back `meta.next_cursor` unchanged. It is opaque, so don't build or edit it |

**200 OK**

```json
{
  "data": [ { "id": 123, "type": "...", "title": "...", "message": "...", "read_at": null, "created_at": "...", "target": null } ],
  "meta": { "per_page": 20, "next_cursor": "eyJjcmVhdGVkX2F0Ijo...", "has_more": true }
}
```

On the last page `next_cursor` is `null` and `has_more` is `false`.

**422** invalid `unread`, `per_page` or `cursor` (keys `unread` / `per_page` / `cursor`; a
cursor that wasn't issued by this endpoint gets `"The cursor is invalid."`).

#### `GET /notifications/unread-count`

**200 OK** `{"count": 4}`. Use it for the bell badge.

#### `POST /notifications/{id}/read`

Marks one of your notifications read. Idempotent: an already-read one keeps its original
`read_at`. Call it when the user taps a notification, then open `target`.

**200 OK**

```json
{ "notification": { "id": 123, "read_at": "2026-10-02T14:05:12+08:00", "...": "..." }, "unread_count": 3 }
```

**404** `{"message": "Not found."}` if the id doesn't exist, isn't a number, or belongs to someone
else (indistinguishable on purpose).

#### `POST /notifications/read-all`

Marks all of your unread notifications read.

**200 OK** `{"marked": 5, "unread_count": 0}`, where `marked` = how many changed.

### Dashboard

#### `GET /dashboard`

Every role (1–4). Returns the signed-in user's dashboard, with the same numbers and sections the
website dashboard shows that user (both are computed by `DashboardAnalyticsService`). It takes no
parameters, and pull-to-refresh simply requests it again.

The response always has the same six keys. Whatever doesn't apply to the role is `null` (for objects)
or `[]` (for lists):

| `role_id` | `student` | `kpis` | `supervised_students` | `action_items` | `recent_activity` |
|---|---|---|---|---|---|
| 1 Student | StudentSummary \| null | `null` | `null` | `[]` | `[]` |
| 2 Internship Coordinator | `null` | Coordinator KPIs | `null` | ActionItem[] | ActivityItem[] |
| 3 Supervisor | `null` | Supervisor KPIs | SupervisedStudent[] | ActionItem[] | ActivityItem[] |
| 4 Administrator | `null` | Administrator KPIs | `null` | ActionItem[] | ActivityItem[] |

Scope: a Student only ever sees their own record. A Supervisor only sees the students assigned to
them (`students.supervisor_id`); every KPI, list and action item is limited to those students.
Coordinators and Administrators are program-wide.

Number formats: hours are numbers rounded to 2 decimals, counts are ints, and percentages are noted
per field. Date-times are ISO 8601 with `+08:00`; date-only fields are `YYYY-MM-DD`.

##### KPIs

Each KPI is `{"value": number, "trend": number | null}`, except `attendance_summary`, which is
`{"present": int, "rejected": int}`. `trend` is the month-over-month change in percent (1 decimal) and
is only set for `total_students`. It is `null` when there is nothing to compare against, and always
`null` for every other KPI. The website's cards are noted in brackets.

| Key | Supervisor | Coordinator | Administrator | Meaning |

### Attendance (Student)

The website's **My Attendance** page. Only Students (1) can use these endpoints, and they always act
on **the signed-in student's own** record; no student or attendance id is accepted. Coordinators,
Supervisors and Administrators get **403** `{"message": "Unauthorized access"}`. The photo endpoint is
the exception: every role can use it, scoped per record (see below).

The rules, the photo storage and the notifications are the same code the website uses
(`AttendanceService`). A leg submitted from the app shows up in the website's Pending Approvals exactly
like one from the website, and the student's supervisor and every Administrator get the same
`attendance_pending` notification.

"Today" is the **Asia/Manila** date. Each day has at most one attendance row with two legs:
time-in and time-out. Each leg is `pending` until a Supervisor or Administrator approves or rejects it,
and `rendered_hours` is credited only once both legs are approved.

**Student account without a student profile** (a rare data problem): every endpoint below except the
photo endpoint answers **409**:

```json
{ "message": "No student profile is linked to your account yet. Please contact your coordinator.", "code": "no_student_profile" }
```

Show the message. This is **not** a logout.

`Content-Type: multipart/form-data`. Every leg needs a live photo and the device's location, the same
as on the website.

| Field | Rules |
|---|---|
| `photo` | required file; an image of type jpg, jpeg, png or webp; at most **5120 KB** (5 MB) and **8000 × 8000 px**. Resize on the phone first (e.g. a 1280 px long edge as JPEG) |
| `latitude` | required number, -90 to 90 |
| `longitude` | required number, -180 to 180 |
| `accuracy` | optional number ≥ 0, in metres. Values above 999999.99 are stored as 999999.99, the same as on the website |
| `mocked` | optional: `1` / `true` = the OS reported the location as mocked, `0` / `false` = not mocked. Leave it out (or empty) if the OS doesn't report it, and it is stored as `null` (unknown). It is **never** a reason to refuse: reviewers see a "possible fake GPS" warning and decide |
| `note` | `emergency-time-out` only: required string, max 1000 characters |

The leg's time is the **server's** time when the request arrives. The app can't send it.

**200 OK**: the success message plus the fresh [`GET /attendance/today`](#get-attendancetoday)
body, so the app can update without a second request:

```json
{
  "message": "Time-in submitted for approval.",
  "date": "2026-10-03",
  "record": { "id": 91, "time_in_status": "pending", "...": "..." },
  "actions": { "time_in": { "allowed": false, "reason": "..." }, "time_out": { "...": "..." }, "emergency_time_out": { "...": "..." } },
  "hours": { "rendered": 120.5, "required": 486, "remaining": 365.5 }
}
```

`message` is `Time-in submitted for approval.`, `Time-out submitted for approval.` or
`Emergency time-out submitted for approval.` (the same as the website's flash messages).

**422** field validation: the standard `{message, errors}` with the keys `photo`, `latitude`,
`longitude`, `accuracy`, `mocked`, `note`. Nothing is stored.

**422** the action isn't allowed in today's state (e.g. a second time-in, or someone else's approval
changed the state since the app last looked). There is no `errors` key, because the problem isn't a
field. Show `message` and re-render from `today`:

```json
{
  "message": "You already have a time-in request for today.",
  "code": "attendance_rule",
  "today": { "date": "2026-10-03", "record": { "...": "..." }, "actions": { "...": "..." }, "hours": { "...": "..." } }
}
```

Nothing is stored and no notification is sent. Re-submitting a **rejected** leg replaces its photo,
location and `mocked` flag, and clears the rejection reason.

Upload size: the server accepts up to 5 MB and 8000 px on either side per photo. A photo over either
limit fails with `422` under `photo`.

Concurrent submissions (a double tap, a retry, two devices) are safe: the state is re-checked under
a row lock, so exactly one succeeds and the others get the `422` `attendance_rule` response above.
Their photos are discarded and no extra notification is sent. Still disable the submit button while
a request is in flight.

#### `GET /attendance/{id}/photo/{leg}`

`{leg}` is `time_in` or `time_out`. Use the `*_photo_url` from an Attendance object rather than
building the URL. The response is the raw image bytes with the stored type (`image/jpeg`, `image/png`
or `image/webp`). Send the usual `Authorization: Bearer` header (e.g. as the image component's
`headers`); there are no signed or public URLs. `Cache-Control: private, max-age=86400`.

Every role can call it, but only for records that role may see on the website: a Student sees their
own, a Supervisor sees their own students', and Coordinators and Administrators see everyone's (used
by later modules).

**404** `{"message": "Not found."}` when the record doesn't exist, isn't yours to see, the leg has no
photo, or `{leg}` isn't `time_in` / `time_out`. These cases can't be told apart on purpose. **401**
without a token.

Each photo is one request against the 120 / minute limit, so load photos when a record is opened (or
lazily as rows come into view) and cache them by URL.

Administrator reviews. List, detail, create, update and delete are **Student (1) only** and only ever
touch **the signed-in student's own** reports; Coordinators, Supervisors and Administrators get
**403** `{"message": "Unauthorized access"}`. The attachment endpoint is the exception: every role can
use it, scoped per report (see below).

Validation, the one-report-per-period rule, attachment storage and notifications are the same code the
website uses (`InternshipReportService`). A report submitted from the app shows up in the website's
Report Reviews like any other, and every Coordinator and Administrator plus the student's supervisor get
the same `report_submitted` notification. When it is reviewed (on the website, or later in the app) the
student gets `report_reviewed`, whose `target` is `my-reports` `{report_id}`: open
[`GET /reports/{id}`](#get-reportsid). Editing and deleting send no notification (same as the website).

**Student account without a student profile:** every endpoint below except the attachment endpoint
answers **409** `{"message": "...", "code": "no_student_profile"}`, exactly as in
[Attendance](#attendance-student).

**Another student's report, or an id that doesn't exist:** **404** `{"message": "Not found."}`. The two
can't be told apart on purpose.

```json
{
  "id": 12,
  "type": "daily",
  "period_start": "2026-10-02",
  "period_end": "2026-10-02",
  "content": "Set up the staging server and wrote the deployment notes.",
  "status": "reviewed",
  "reviewer_comment": "Good detail.",
  "reviewer": { "id": 5, "name": "Maria Santos" },
  "reviewed_at": "2026-10-03T09:12:00+08:00",
  "attachment": {
    "name": "Proof of work.pdf",
    "mime": "application/pdf",
    "kind": "pdf",
    "size": 48213,
    "url": "https://<host>/api/v1/reports/12/attachment?v=3f1c2a9b0d4e"
  },
  "created_at": "2026-10-02T17:40:11+08:00",
  "updated_at": "2026-10-03T09:12:00+08:00",
  "can_edit": false,
  "can_delete": false
}
```

| Field | Type | Notes |
|---|---|---|
| `id` | int | |
| `type` | string | `daily` \| `weekly` |
| `period_start`, `period_end` | string | `YYYY-MM-DD`. Equal for a daily report |
| `content` | string | The accomplishment text as typed (line breaks kept) |
| `status` | string | `pending` \| `reviewed` |
| `reviewer_comment` | string \| null | The reviewer's comment. It can be `null` on a reviewed report, because the comment is optional |
| `reviewer` | `{id: int, name: string}` \| null | Who reviewed it. `null` while pending, and also if the reviewer's account was deleted since |
| `reviewed_at` | string \| null | ISO 8601 with `+08:00`; `null` while pending |
| `attachment` | object \| null | `null` = no attachment (or its file is missing on the server) |
| `attachment.name` | string | File name to show / save as: the student's original name, cleaned up (at most 255 characters, no control characters, and the extension always matches the real file type) |
| `attachment.mime` | string | `image/jpeg`, `image/png` or `application/pdf` |
| `attachment.kind` | string | `image` \| `pdf` (`file` for anything else, which validation doesn't currently allow) |
| `attachment.size` | int | Bytes |
| `attachment.url` | string | Absolute URL of the [attachment endpoint](#get-reportsidattachment). The `?v=` part changes whenever the file is replaced, so the app can cache by URL |
| `created_at`, `updated_at` | string | ISO 8601 with `+08:00` |
| `can_edit`, `can_delete` | bool | Whether the signed-in user may edit / delete it right now (own report, still `pending`). Show the buttons from these rather than working the rule out in the app |

#### `GET /reports`

The student's own reports, newest period first (`period_start`, then `id`, descending: the website's
order), cursor-paginated like [`GET /notifications`](#get-notifications).

| Query | Rules |
|---|---|
| `type` | optional: `daily` \| `weekly` (empty = all) |
| `status` | optional: `pending` \| `reviewed` (empty = all) |
| `per_page` | optional int, 1–50, default 20 |
| `cursor` | optional; pass back `meta.next_cursor` unchanged, with the same filters |

**200 OK**

```json
{
  "data": [ { "id": 12, "type": "daily", "...": "..." } ],
  "meta": { "per_page": 20, "next_cursor": "eyJwZXJpb2Rfc3RhcnQiOi...", "has_more": true }
}
```

**422** invalid `type`, `status`, `per_page` or `cursor` (a cursor this endpoint didn't issue gets
`"The cursor is invalid."`).

#### `GET /reports/{id}`

**200 OK** `{"report": { ...Report object... }}`. **404** if it isn't yours.

#### `POST /reports`

`Content-Type: multipart/form-data` (or JSON when there is no attachment).

| Field | Rules |
|---|---|
| `type` | required: `daily` \| `weekly` |
| `period_start` | required date, `YYYY-MM-DD` |
| `period_end` | required date, `YYYY-MM-DD`, on or after `period_start`. For a **daily** report it must equal `period_start` (send the same date twice) |
| `content` | required string, at most **16000** characters |
| `attachment` | optional file: jpg, jpeg, png or pdf, at most **5120 KB** (5 MB). Images at most **8000 × 8000 px** |

The file type is decided by the file's **content**, not its name: SVG, HTML, scripts, archives and
anything else renamed to `.jpg` / `.png` / `.pdf` are refused (`422` under `attachment`). A file whose
name doesn't match its type is stored with the right extension (a PDF named `notes.html` is offered
back as `notes.pdf`).

A student can have only **one report of each type per `period_start`**. A second one (or an edit that
would collide with another of your reports) is `422` with
`errors.period_start = ["You've already submitted a daily report for this period."]` (or `weekly`).
Two identical submissions at the same moment (double tap, retry) are safe: exactly one is stored and
the other gets this same `422`, with its file discarded and no extra notification.

**201 Created**

```json
{ "message": "Report submitted for review.", "report": { "id": 12, "status": "pending", "...": "..." } }
```

**422** field validation (keys `type`, `period_start`, `period_end`, `content`, `attachment`). Nothing
is stored and nobody is notified.

#### `POST /reports/{id}` with `_method=PATCH` (update)

Send it as **`POST` with a form field `_method=PATCH`** and a `multipart/form-data` body: PHP doesn't
read multipart bodies on a real `PATCH`. A real `PATCH /reports/{id}` also works, but only with a JSON
body (so without a file).

Only a **pending** report can be changed. All the `POST /reports` fields are sent again (full replace,
same rules, same duplicate check against your *other* reports), plus:

| Field | Rules |
|---|---|
| `attachment` | optional: a new file **replaces** the current one (the old file is deleted). Leave it out to keep the current attachment |
| `remove_attachment` | optional: `1` / `true` removes the current attachment without a replacement; `0` / `false` / empty / omitted keeps it. As text in multipart, or as a JSON boolean or number. Anything else is `422`, and so is `1` together with a new `attachment` (both under `remove_attachment`) |

**200 OK** `{"message": "Report updated.", "report": { ... }}`

#### `DELETE /reports/{id}`

Only a **pending** report. Its attachment file is deleted too.

**200 OK** `{"message": "Report deleted."}`

#### Refusal: the report is no longer pending

Updating or deleting a report that has been reviewed (including one reviewed while the app was still
showing it as pending) is `422` with a `code` and no `errors` key, because the problem isn't a field.
The body carries the fresh report so the app can re-render it:

```json
{
  "message": "This report has already been reviewed and can no longer be changed.",
  "code": "report_not_pending",
  "report": { "id": 12, "status": "reviewed", "can_edit": false, "can_delete": false, "...": "..." }
}
```

Nothing changes and an uploaded file is discarded. The check is repeated under a row lock, so a review
and an edit/delete arriving together can't both win. If the report was deleted meanwhile (e.g. from
another device), the answer is `404`.

#### `GET /reports/{id}/attachment`

Use `attachment.url` from a Report object rather than building the URL. Send the usual
`Authorization: Bearer` header; there are no signed or public URLs.

The response is the raw file with:

| Header | Value |
|---|---|
| `Content-Type` | `image/jpeg`, `image/png` or `application/pdf` (detected from the stored bytes) |
| `Content-Disposition` | `inline; filename="<name>"`, plus `filename*=utf-8''<url-encoded name>` when the name isn't plain ASCII (then `filename` is an ASCII fallback). `<name>` = `attachment.name` |
| `Cache-Control` | `private, max-age=86400` |
| `X-Content-Type-Options` | `nosniff` |
| `Content-Security-Policy` | `default-src 'none'; sandbox` |

Every role can call it, but only for reports that role may see on the website: a Student their own, a
Supervisor their own students', Coordinators and Administrators everyone's (Module 11 uses this).

**404** `{"message": "Not found."}` when the report doesn't exist, isn't yours to see, or has no file.
**401** without a token. Each download counts against the 120 / minute limit.

### Feedback (Student)

The website's **My Feedback** page: the evaluations a supervisor wrote about the signed-in student.
Read-only, **Student (1) only**; Coordinators, Supervisors and Administrators get **403**
`{"message": "Unauthorized access"}`. Only **the student's own** evaluations with status `submitted` or
`locked` are ever returned; drafts never are (same rule as the website, `EvaluationService::studentFeedback()`).

No notification or dashboard action item points at My Feedback (submitting an evaluation notifies no
one), so there is no `target` screen for it: the app opens it from its menu.

**Student account without a student profile:** both endpoints answer **409**
`{"message": "...", "code": "no_student_profile"}`, exactly as in [Attendance](#attendance-student).

**A draft, another student's evaluation, or an id that doesn't exist:** **404** `{"message": "Not found."}`.
They can't be told apart on purpose.

#### Feedback summary object

```json
{
  "id": 7,
  "period_start": "2026-09-01",
  "period_end": "2026-09-30",
  "status": "submitted",
  "overall_rating": 4.25,
  "rating_max": 5,
  "supervisor": { "id": 5, "name": "Maria Santos" },
  "company": { "id": 2, "name": "Acme Corp" },
  "submitted_at": "2026-10-01T10:15:00+08:00",
  "locked_at": null
}
```

| Field | Type | Notes |
|---|---|---|
| `id` | int | |
| `period_start`, `period_end` | string | `YYYY-MM-DD`, the evaluation period |
| `status` | string | `submitted` \| `locked` (an Administrator locked it; nothing changes for the student) |
| `overall_rating` | number \| null | Average of the criterion ratings, 2 decimals (the website shows it as `4.25/5`). `null` if nothing was rated |
| `rating_max` | int | Always `5` |
| `supervisor` | `{id, name}` \| null | Who wrote it (the supervisor at the time). `null` if none was assigned or the account was deleted |
| `company` | `{id, name}` \| null | The host company at the time; `null` if none or deleted |
| `submitted_at`, `locked_at` | string \| null | ISO 8601 with `+08:00` |

#### Feedback detail object

The summary fields plus:

```json
{
  "strengths": "Fast learner",
  "areas_for_improvement": "Documentation",
  "recommendations": null,
  "supervisor_remarks": "Keep it up.",

    {
      "category": "Work Quality",
```

| Field | Type | Notes |
|---|---|---|
| `strengths`, `areas_for_improvement`, `recommendations`, `supervisor_remarks` | string \| null | Free text as typed (line breaks kept). The website hides a section that is `null`/empty; its label for `supervisor_remarks` is "Supervisor Remarks" |
| `categories` | array | The **saved** ratings grouped by category, in the website's order. Built from what was rated, not from today's criteria list: a criterion deactivated or edited since still shows its rating; one added since doesn't appear |
| `categories[].criteria[].id` | int | Criterion id |
| `label`, `description` | string, string \| null | The criterion's current wording |
| `rating` | int | 1–5 |
| `max` | int | Always `5` |
| `comment` | string \| null | The supervisor's per-criterion comment |

## curl quick start

```bash
# Log in
curl -s -X POST http://127.0.0.1:8000/api/v1/login \
  -H "Accept: application/json" -H "Content-Type: application/json" \
  -d '{"email":"juan@example.com","password":"secret","device_name":"curl"}'

# Use the token
curl -s http://127.0.0.1:8000/api/v1/me \
  -H "Accept: application/json" -H "Authorization: Bearer 12|Xb4QkPz8mN2..."

# Time in (Student; multipart)
curl -s -X POST http://127.0.0.1:8000/api/v1/attendance/time-in \
  -H "Accept: application/json" -H "Authorization: Bearer 12|Xb4QkPz8mN2..." \
  -F "photo=@selfie.jpg" -F "latitude=10.6765432" -F "longitude=122.9509876" \
  -F "accuracy=12.5" -F "mocked=0"

# Submit a daily report (Student; multipart)
curl -s -X POST http://127.0.0.1:8000/api/v1/reports \
  -H "Accept: application/json" -H "Authorization: Bearer 12|Xb4QkPz8mN2..." \
  -F "type=daily" -F "period_start=2026-10-02" -F "period_end=2026-10-02" \
  -F "content=Set up the staging server." -F "attachment=@proof.pdf"

# Edit it (multipart update = POST + _method=PATCH)
curl -s -X POST http://127.0.0.1:8000/api/v1/reports/12 \
  -H "Accept: application/json" -H "Authorization: Bearer 12|Xb4QkPz8mN2..." \
  -F "_method=PATCH" -F "type=daily" -F "period_start=2026-10-02" -F "period_end=2026-10-02" \
  -F "content=Set up and documented the staging server." -F "remove_attachment=1"

# Log out
curl -s -X POST http://127.0.0.1:8000/api/v1/logout \
  -H "Accept: application/json" -H "Authorization: Bearer 12|Xb4QkPz8mN2..."
```

## Changelog

- **Module 1** — `POST /login`, `POST /logout`, `GET /me`; error format; rate limits.
- **Module 1 revision (2026-10-02)** — the API is open to all four roles. Coordinators and
  Administrators can log in (previously `403 role_not_allowed`); `role_not_allowed` now only
  covers accounts with no role and has a new message. `GET /me` gained the `staff` key
  (StaffPermissions for roles 2/4, `null` otherwise).
- **Module 4** — Notifications: `GET /notifications` (cursor-paginated, `?unread=1`),
  `GET /notifications/unread-count`, `POST /notifications/{id}/read`, `POST /notifications/read-all`;
  Notification object with `target` `{screen, params}` (screen keys table).
- **Module 5** — Dashboards & Analytics: `GET /dashboard` (role-aware: student summary,
  supervisor/coordinator/admin KPIs, supervised students, action items with `target`, recent
  activity with `is_own`), `GET /analytics` (plain series, website filters, Supervisor-scoped,
  roles 2–4), `GET /analytics/filter-options`. New screen key `evaluations` (used by action items).
  For a Supervisor, a nonexistent `student_id` / `company_id` is `403` (same as out of scope), not
  `422`, and `supervisor_id` is ignored without an existence check.
- **Module 6** — Student attendance: `GET /attendance/today` (record, allowed actions with
  reasons, hours), `GET /attendance` (cursor-paginated history), `POST /attendance/time-in`,
  `/time-out`, `/emergency-time-out` (multipart: photo, GPS, `mocked`), and
  `GET /attendance/{id}/photo/{leg}` (any role, scoped, `404` when not visible). New Attendance
  object, new `422` `code: attendance_rule` and `409` `code: no_student_profile`. Fake-GPS flags
  `time_in_mocked` / `time_out_mocked` are stored and shown to reviewers on the website.
- **Module 6 QA fixes** — (website too) a rejected time-in can't be re-submitted once the day's
  time-out is pending or approved (new `time_in` refusal reason; it used to credit negative hours);
  photos are limited to 8000 × 8000 px; concurrent submissions of a leg: exactly one wins.
- **Module 7** — Student reports: `GET /reports` (cursor-paginated, `type` / `status` filters),
  `GET /reports/{id}`, `POST /reports` (multipart), update via `POST /reports/{id}` + `_method=PATCH`
  (with the app-only `remove_attachment`), `DELETE /reports/{id}`, and `GET /reports/{id}/attachment`
  (any role, scoped, `404` when not visible). New Report object (with `can_edit` / `can_delete`) and new
  `422` `code: report_not_pending`. Shared with the website: period dates must be `YYYY-MM-DD`, a daily
  report's `period_end` must equal its `period_start`, `content` is capped at 16000 characters, image
  attachments at 8000 × 8000 px; stored file names are cleaned up; racing duplicate submissions are a
  `422` (not a `500`); edit/delete re-check "pending" under a row lock.
- **Module 8** — Student feedback: `GET /feedback` (cursor-paginated, own `submitted` / `locked`
  evaluations only, never drafts) and `GET /feedback/{id}` (saved ratings grouped by category, free-text
  sections). New Feedback summary / detail objects. No new screen key: nothing links to My Feedback.
- **Module 9** — Pending Approvals (Supervisor = own students, Administrator = all; Coordinator and
  Student `403`): `GET /approvals` (cursor-paginated, newest first), `GET /approvals/count`,
  `GET /approvals/{id}`, and `POST /attendance/{id}/time-in/approve`, `/time-in/reject`,
  `/time-out/approve`, `/time-out/reject` (optional `reason`, max 500). New Approval object (Attendance
  object + `student`, `pending_legs`, `review` flags). A leg that is no longer pending is a `422`
  `code: attendance_rule` with the fresh `attendance`; a record you can't review is a `404`.
